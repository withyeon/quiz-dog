# 중계 서버 측정 결과 (2026-10-16)

## 결론

AWS Lightsail 서울 $7 플랜(1GB, vCPU 2개, 기준 성능 10% = vCPU 0.2개분)에서 **여유 30%를 남기고 계속 유지할 수 있는 양**:

| 방 종류 (25명 + 교사 화면) | 계속 유지 (기준 성능) | 수업 시간대만 몰릴 때 (아래 조건) | 잠깐 최대 (크레딧 있을 때) |
|---|---|---|---|
| 퀴즈형 | **약 35개 방 (학생 약 870명)** | 약 140개 | 약 350개 |
| 점프점프 | **약 6개 방** | 약 24개 | 약 60개 |

- 섞어 쓰면 퀴즈형 방 1개 ≈ vCPU 0.004개, 점프점프 방 1개 ≈ vCPU 0.023개로 더한다. 예: 퀴즈형 20개 + 점프점프 2개 = 0.126 < 0.14(기준 성능의 70%) → 기준 성능 안에서 된다.
- 한계는 CPU다. 메모리(연결 1개당 약 35KB)와 데이터 전송량(월 2TB)은 이 규모에서 한참 남는다.
- "수업 시간대만 몰릴 때"는 밤 18시간 동안 쉬어서 버스트 크레딧이 약 100분 이상 쌓여 있고, 낮 6시간 동안 평균 CPU 40%까지 쓰는 경우다.
  Lightsail의 최대 적립량은 확인하지 못했다. 그러니 계획은 왼쪽 열(기준 성능)로 세우는 게 안전하다.
- **가장 큰 불확실성은 환산 계수다.** M4 성능 코어 1개를 Lightsail vCPU 3개분으로 잡았다(가능 범위 2.5~4배).
  실제 Lightsail 인스턴스에서 `relay/loadtest.mjs`를 한 시간만 돌려 보면 확정된다(비용 몇 원).

Supabase와 비교 (25명 방 하나, 초당 메시지, 보내고 받은 것 모두):

| | Supabase (1번 수정 후) | 중계 서버 |
|---|---|---|
| 퀴즈형 | 평균 약 118 | 약 107 (서버가 받은 것 + 보낸 것, ack 포함) |
| 점프점프 | 순간 최대 약 2,100~4,000 | 약 406 (좌표 묶음 덕분에 5~10배 적음) |

퀴즈형은 메시지 수가 거의 같다(모두에게 뿌리는 건 그대로라서). 차이는 메시지당 요금과 초당 한도(Pro 500/s → 방 2개)가 없다는 점이다.

## 어떻게 쟀나

- 장소: Apple M4 맥(10코어, 16GB). 서버 `node relay/server.mjs` 한 프로세스, `ws://127.0.0.1` (TLS는 따로 쟀다).
- 부하: [loadtest.mjs](loadtest.mjs)가 방마다 학생 25명 + 교사 화면 1개를 실제 WebSocket 클라이언트로 띄운다(프로세스 4개로 나눠서).
  /dev 봇은 자기 탭 안에서만 이벤트를 흘려서 네트워크 부하를 만들지 못한다. 그래서 같은 규칙을 따르는 부하 생성기를 따로 만들었다.
  - 퀴즈형: 학생마다 평균 6초(최소 1.5초)에 한 문제 → `player:patch` 1개. 45초 presence 하트비트, 25초 앱 핑.
  - 점프점프: 60%는 움직이는 중. 움직이면 300ms, 멈추면 1.5초마다 좌표를 보내고, 움직이는 동안 2초마다 `player:patch`.
- 한 판: 10초 워밍업 뒤 40초 측정. 서버 `/metrics`를 5초마다 읽어 평균을 냈다. CPU는 서버 프로세스만, 코어 1개 = 100%.
- 지연: 교사 화면 클라이언트가 받은 이벤트마다 (받은 시각 − 보낸 시각). 같은 기계라 네트워크 지연은 빠져 있다.

```bash
node relay/server.mjs &
node relay/loadtest.mjs --rooms 40 --mode quiz --seconds 40
node relay/loadtest.mjs --rooms 10 --mode dld --seconds 40
```

### TLS(`wss://`) 비용

같은 부하를 노드가 직접 TLS를 처리하게 해서 쟀다(RSA 2048 자체 서명 인증서).

| | 평문 | TLS | 배수 |
|---|---|---|---|
| 퀴즈형 40개 방, 메시지 1개당 CPU | 9.4 µs | 13.6 µs | 1.45배 |
| 점프점프 10개 방, 메시지 1개당 CPU | 10.4 µs | 18.3 µs | 1.75배 |

**접속 폭주:** 초당 1,600개를 한꺼번에 붙이면 RSA 인증서에서는 18%가 ECONNRESET으로 끊겼다(초당 400개는 전부 성공).
ECDSA(P-256) 인증서로 바꾸면 같은 조건에서 1,040개 중 1개만 끊겼고, 초당 3,000개에서도 96%가 붙었다.
→ 운영에서는 **ECDSA 인증서**를 쓴다(Caddy·Let's Encrypt 기본값). 클라이언트 재연결 간격에는 ±50% 흔들기를 넣어,
서버 재시작 때 전원이 같은 순간에 몰리지 않게 했다.

## Lightsail 환산

| | 퀴즈형 방 1개 | 점프점프 방 1개 |
|---|---|---|
| M4 코어 사용률 (평문) | 0.09% | 0.43% |
| × TLS | 1.5배 → 0.135% | 1.8배 → 0.77% |
| × Lightsail 환산(3배) | vCPU 0.004개 | vCPU 0.023개 |

예산(여유 30% 남김): 기준 성능 0.2 × 0.7 = **vCPU 0.14개**, 수업 시간대 평균 0.8 × 0.7 = 0.56개, 잠깐 최대 2 × 0.7 = 1.4개.

- 메모리: 연결 4,160개에서 RSS 198MB → 1GB 인스턴스는 연결 1만 개 이상에서야 빠듯해진다.
- 전송량: 40분 한 판에 퀴즈형 약 75MB, 점프점프 약 370MB → 월 2TB면 퀴즈형 약 2만 6천 판, 점프점프 약 5천 판.
- 지연: 이 맥에서 서버가 더한 지연은 퀴즈형 p99 2ms 이하, 점프점프 40개 방에서 10ms. Lightsail은 CPU가 느리지만,
  기준 성능 안의 부하라면 수십 ms 안쪽일 것으로 본다. 여기에 서울 리전 왕복 5~10ms가 더해진다.

## 앱에서 직접 확인한 것 (localhost:3002, 별도 작업 트리)

- 중계 모드(`NEXT_PUBLIC_ROOM_TRANSPORT=relay`), 탭 2개:
  - 로비에 "온라인 2명 · 실시간 연결됨"이 떴다(presence).
  - 골드 퀘스트에서 A가 상자를 열면 B 화면 순위에 0.3초 안에 반영됐다(`player:patch`).
  - 로비 → 게임으로 넘어갈 때 다시 입장했다.
  - 점프점프 좌표 묶음이 B에서 원래 `dontlookdown:pos` 이벤트로 풀렸다(보낸 사람 playerId 일치).
  - **중계 서버를 껐다 켜자** 두 탭 모두 5초 안에 스스로 다시 입장했고, presence도 돌아왔다.
- 기본 모드(환경 변수 없음), 탭 2개: Supabase 소켓만 썼고, presence("온라인 2명")와 `player:patch` 전달(0.18초)이 전과 같았다.

## 남은 개선 거리 (측정에서 보인 것)

- 점프점프 묶음의 playerId(36자)를 방 안 번호로 바꾸면 보내는 데이터가 절반 가까이 준다.
- 좌표 이벤트에는 ack가 필요 없다(바로 다음 좌표가 덮어쓴다). 빼면 점프점프의 서버→클라이언트 메시지가 약 20% 준다(10개 방 측정에서 ack가 초당 약 700개).
- 실제 게임 모드(골드 퀘스트 공격, 배틀 효과 등)는 이 모델보다 이벤트가 20~50% 많을 수 있다. 위 방 수는 그만큼 여유를 두고 읽는다.
